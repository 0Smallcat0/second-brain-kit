# Writing for others

For anything the user will send or show to other people: an application, a CV, a cover or request letter, a report, a presentation, a reply to a message. Do these three things in order: prepare, write, check. It is the user's words and the user's facts; your job is to make them land.

## 1. Before writing: three tables
Keep them in a scratch file or the notes folder, not in the document.
- **Requirements table.** One row per recipient or per document: every item to hand in, page or word limits, language, format, each deadline. Read the rules as written; do not make them stricter and do not treat what is not written as a rule. Put the source (page, link, message) next to every cell. What the user already answered is not asked again.
- **Materials table.** For every field the document will ask about, sweep the notes folder and the user's files once and list all candidates with where the proof is, then choose. Do this before writing, so nothing the user has done is left out because you did not look.
- **Main line per document.** One sentence: "this document must make the reader believe ___". Pick the materials that prove that sentence. Documents for different recipients differ in which materials, in what order, and how they end; changing the name is not tailoring.

## 2. Writing
- Use the user's own words and facts, each traceable to a source (a note line, a file, something the user said and when). A fact that follows from sourced facts may be used if you mark what it follows from; anything else is left out.
- Write only the strongest true parts. Do not write weaknesses, hedges or self-criticism unless a written rule requires them. If you are unsure that something is the user's own experience, ask; do not delete it silently and do not assume it.
- Say the same thing the same way in every document: fix one standard sentence for each repeated fact and copy it.
- For reports, proposals and briefs for an adviser or a teacher, put the answer first (what is known, what changed, the answer), then 3-5 supporting points that do not overlap and do not leave a gap, with headings that are statements ("cheaper than hiring one more person", not "Cost"), in one consistent order. Stories, statements of purpose, reflections and letters do not use this shape.
- When the user gives an order, a name or a place for the files, that is the specification.

## 3. Revising and outside opinions
- After the draft, change only two kinds of things: facts (anything not in the sources is fixed or removed) and rule compliance (limits, format, required items). Leave the rest of the voice and structure alone.
- Sort every comment, from the user, another AI or an adviser, into four: needs a change; it is wrong; deliberate; does not matter. Change only the first kind, and write the reason for every other kind. Never accept a batch whole or reject a batch whole. A comment that says "no change needed" is also an opinion: reread that document yourself.
- Do not take advice to add caveats, limits or disclosures when no written rule requires them.
- When one mistake is found, name its kind (an undefined term, a weakness sentence, the main line coming too late, one fact told two ways, a fact error, layout), then sweep every document still to be handed over for the same kind and fix them all. Report how many documents you swept and how many more you found.
- Hand over the changes with the user's words kept; list what you deleted or rewrote and why.

## 4. Before handing over
- **Cold read.** Open a fresh subagent that has not seen the drafting. Give it the finished documents in the order the reader will see them, the questions the recipient will ask, and the decisions the user has made that it must not suggest changing. First ask it to say in its own words, in 2-5 sentences per document, what the document wants the reader to believe, who the main character is and what holds it up; a document where it cannot do that is the problem. Then ask: which names or terms are still unclear after reading; which sentences read like a weakness, a caveat or a defence; whether the main line shows up in the first paragraph; contradictions across documents; references ("see attached") with nothing behind them; and anything uncertain written as settled. Check each thing it finds against the sources before changing anything.
- **Fact table.** Under the document, add a table: one row for every factual claim (who, which address, which date, what status, what the recipient will receive or do), each with its source (message id and date, a screenshot path, an official page and the quoted sentence). A claim with no source is deleted or marked as a guess. Give the table to the checking subagent and ask it to compare row by row against the sources.
- **Report what you checked.** Say which documents and which checks; if you looked at one of four, say "looked at one", never "all fine". Look at the final file or page itself, not the draft.
- Letters and messages: the user presses send; prepare it so that only that press is left.

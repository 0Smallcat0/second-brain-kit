# 踩過的坑：出過什麼錯，套件怎麼處理

這些來自每天用 Claude 好幾個月的經驗，每一條都是真的發生過的錯。套件預設已經包含修法；這頁說明原因，避免你不小心拆掉它。

## 1. 規則寫了，卻沒被執行
`CLAUDE.md` 裡寫了「說完成前一定要驗證」，出錯那一刻規則就在上下文裡，還是錯了。規則檔越長，被遵守的比例越低。
**做法：** `CLAUDE.md` 保持精簡（100 行內），把檢查放進「動作當下」的程式：看工具呼叫的 hook、拒絕提交的腳本。一條規則一直被違反時，不要再多寫一句，把它改成檢查。

## 2. 關卡太多，反而做不完
會永遠拒絕的完成關卡比沒有更糟：計數（「還缺 2 項」）永遠到不了零，因為它要數的東西根本產不出來；驗證回合連續六次用同一種方式失敗；第三個對話要等第二個對話批准。
**做法：** 每個關卡都要能放手。Stop hook 每一輪只擋一次（`stop_hook_active` 代表「已經問過了，放行」）。沒有任何事要等別的對話批准；主題對話自己附證據關掉帳本項目。要加關卡時，先用一句話寫出「檢查過不了時，它怎麼結束」。

## 3. 審批鏈太長
需求 → 入口 → 主題 → 審查 → 入口 → 使用者：每一跳都可能卡住，每一跳也都要把所有東西重讀一遍。
**做法：** 只有入口加主題對話。入口分派與追蹤；主題對話做事、附證據關掉項目；使用者看結果。

## 4. 鬧鐘會自己變多
輪詢式鬧鐘（「每 10 分鐘看一下 X 發生了沒」）和「為了追問鬧鐘而設的鬧鐘」，一天內從幾十個長到快八十個，每個都叫醒一個對話、再製造更多工作。
**做法：** 只有每天／每週／一次三種；觸發只寫帳本或收件匣，同一個沒處理完的不重複寫；超過 20 列就警告；`--prune` 清掉已觸發的一次性列。沒人處理的鬧鐘就刪掉。

## 5. 額度浪費在無聊的地方
- 最貴的模型拿去跑迴圈和機械工作。
- 一張大表重複送給付費 API 七次，用掉大約半個月的預算；其實只要送有變的部分。
- 第二組額度大半閒置，主帳號卻先用完。
- 在前景輪詢一個其實可以丟出去、之後再讀結果的工具。
**做法：** 每件工作各自選模型與 effort（機械的用便宜、低 effort 的）；只送有變的部分；大工作前先看週用量（`usage_warn` 在 80% 提醒）；長工作丟背景、寫成結果檔。

## 6. 額度被鎖，佇列默默停住
有些工具用完會鎖好幾天（有一次鎖了大約六天）。派給它的工作就一直擺著。
**做法：** 在派工的地方（`channels.md`）寫「鎖到何時」，派工前先看。見 [參考-多工具分工](參考-多工具分工.md)。

## 7. 瀏覽器分頁和檔案越堆越多
自動化工作會開視窗、分頁、暫存檔，卻不關。
**做法：** 每個自動化工作的結尾都寫「關掉自己開的，原本開著的不動」，之後自己數一次分頁。暫存檔放在固定的一個資料夾，不要散在使用者的工作旁邊。

## 8. 用字眼檢查，換個說法就繞過去
檢查「done」這個字，會被「這樣應該都好了」繞過；檢查禁用詞，只會讓模型改用別的詞。
**做法：** 檢查事實，不檢查字眼。Stop hook 真正的判斷是工具呼叫的順序（最後一次修改之後，有沒有讀回或執行過？），字眼只是觸發條件。帳本沒有證據文字就不讓關。仍會有漏洞，要看紀錄檔。

## 9. 新檢查：先只記錄，再開始擋
新加的擋人檢查一旦誤擋，損失的信任比它防的錯還大。
**做法：** 每個 hook 都有模式（`off、log、warn、ask、deny、block`）。新的或改過的檢查先用 `log`，幾天後讀 `logs/*.log`，再決定要不要擋。

## 10. 新檢查先拿過去的錯誤重播
**做法：** 對真實的舊對話跑 `python hooks/stop_evidence.py --replay <transcript.jsonl>`，它會列出哪幾輪會被擋。誤擋太多就維持 `log`。沒看過真實案例的檢查只是猜測。

## 11. 沒打開實物就說做完
工具回報「成功」，但檔案寫到錯的資料夾、上傳漏了一個欄位、腳本什麼都沒做卻回傳 0。
**做法：** `evidence-before-done` 技能加 Stop hook。打開檔案、跑測試、把頁面讀回來，並說出看到了什麼。

## 12. 多件事，修一件丟一件
**做法：** 三件以上用 `task.md`，每一項照使用者的原話抄下來，並寫完成條件；最後的回覆逐項寫完成／沒完成與原因。

## 13. 只指出問題就停
「X 被擋住了，你需要……」然後就沒了。
**做法：** 做到只剩使用者才能做的那一步（密碼、驗證碼、付款、簽名、決定），其他全部備好，再把他最少要做的寫成編號清單。`todo-for-me.md` 就是這份清單，裡面不能放 Claude 自己做得到的事。

## 14. 入口自己動手做事
入口對話一開始做長工作，上下文就被塞滿，忘了分派，帳本也不再更新。
**做法：** 入口的 `CLAUDE.md` 寫明：短問題直接答，其他都登記、交給主題對話、查帳本。

## 15. 帳本和 task.md 腐爛
項目一直不關；`task.md` 還寫著早就做完好幾週的「進行中」。
**做法：** `ledger.py list` 會標出超過 14 天的項目；預設的每週鬧鐘就是檢討；項目只有附證據、或由使用者明說不做才關。

## 16. 方向自己一個人定
大選擇（做什麼、用什麼策略、什麼設計）只根據一個模型的第一個想法。
**做法：** 寫下需求和事實、不放自己的方案，盲問第二個模型（網頁版就夠），比較之後再選。見參考-多工具分工。

## 17. 回覆太長
使用者要的是答案和要他決定的事，不是過程。
**做法：** 答案放最前面、短、用使用者的語言；細節他問才給。

## 18. 讀一小段就下結論
`head -20 note.md` 之後信心十足地回答，結果後面的內容推翻了它。
**做法：** `read_whole` 會拒絕對庫裡的筆記做片段讀取；原則寫明要讀到最後一行、並說出讀了多少。

## 19. 壓縮把需求改寫了
長對話被摘要之後，使用者原本的字句不見了，摘要悄悄改掉目標。
**做法：** `requests_reinject` 在壓縮後把使用者自己的訊息原文放回來，完整清單另存成檔。

## 20. 文件和程式不一致
README 承諾了一個程式沒有的指令，或程式根本不看的設定。
**做法：** `scripts/selftest.py` 會跑一次文件裡提到的每個 hook 和工具。改了其中一個就跑一次。文件和程式不同時，以程式為準，去修文件。

## 21. 過度設計
每多一個機制，就多花 token、注意力，也多一個會壞的地方。
**做法：** 加規則、hook 或表格之前，先寫下它防的是哪個真的發生過的錯；寫不出來就不加。從入口加兩個主題對話開始；某一個太擠時才加。

## 22. 只在一台電腦能跑的 hook
寫死的路徑、只有 Windows 才有的呼叫、JSON 行開頭的 BOM。
**做法：** hook 只用 Python 3 標準函式庫，經 `hooks/run.sh` 啟動（它會找存在的那個 Python），任何內部錯誤都 exit 0（fail-open），壞掉的 hook 不會把對話卡死。
